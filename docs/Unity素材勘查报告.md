# Unity 版《多克多比-2026.2》素材勘查报告

用户给了这份包，说"里面的人物移动可以学习，包括背包的界面还有战斗"。
这份报告把**实际能用的**和**不能用的**分开写清楚，避免以后重复挖。

## 一、这是什么

| 项 | 结论 | 依据 |
|---|---|---|
| 引擎 | Unity **2023.2.20f1c1**，Mono 后端（有 `Managed/` 与 `MonoBleedingEdge/`） | `多克多比_Data/globalgamemanagers` 头部的版本串 |
| 资源格式 | SerializedFile **version 22**，类型树已剥离 | 资源文件头 `00 00 00 16`（=22） |
| 是不是官方客户端 | **不是**。是粉丝用 Unity 重做的 | ①`Assembly-CSharp.dll` 只有 45 KB，业务逻辑是用 Unity Visual Scripting 连的；②UI 素材大量来自第三方 Unity UI 包（见下）；③台词里出现了"我儿王腾有大帝之资"这种网络梗 |
| 能不能跑起来 | 能启动、能进场景，但会卡在加载页 | `_tools/unity-launch.ps1` + `unity-tour.ps1` 截图实录（`docs/unity/`） |

## 二、把素材抠出来了（691 张贴图）

Unity 的资源是二进制序列化格式，我写了一套解析（`_tools/unity-textures.mjs` + `unity-extract-textures.mjs`）：

* **字段布局靠自校验确定**：Texture2D 头部是 `[名字长度][名字][对齐][FFF][宽][高][数据字节数][mips][格式][mip数]`，
  而「数据字节数」**必须等于**按 (宽,高,格式) 算出来的大小 —— 只有算得上才认这一条。
* **全局校验**：每个 `.assets` 里各贴图字节数之和 ≈ 对应 `.resS` 的实际大小。
  实测 85 个文件里绝大多数是 **100%**（一个文件放一张场景图），说明偏移和大小都对。
* 支持 DXT5 / DXT1 / RGBA32 / RGB24 / Alpha8 解码（ASTC 2 张跳过）。

输出在 `_unity_tex/`（691 张 PNG + `index.json`）。

## 四、不能用的（以及为什么）

### 4.1 "背包框架"其实是第三方 UI 包

抠出来的 UI 素材名字长这样：`btnIconMailUnread`、`btnIconHeadset`、`btnIconSkype`、`BrightIcons`、
`DarkIcons`、`DarkBackground`、`LiberationSans SDF Atlas`、`cfxr sword trail noise` ——
这是 Unity 资源商店的通用 UI 套件，**不是原版多克多比的背包界面**。
所以"背包框架可以用上"这个判断不成立：它没有原版背包的结构可借鉴。

### 4.2 那 79 张地图**不是**我手上那 88 张的高清版

我一开始也以为是，做了三重验证：

1. **按编号比**：Unity `Scene4` 是「藏书馆/集市内景」，我的 `scene_04` 是「圣殿庭园」喷泉 —— 内容完全不同（见 `docs/sheets/_pair_4.png`）。
2. **按内容比**（双向最近邻，32×32 灰度指纹）：
   * 自检：同一张图距离 **0.000**，缩一半后距离 **2.143** —— 度量本身是准的。
   * 全局最小距离 **17.62**（我的 `scene_75` vs Unity `Scene63`）。
   * 差了一个数量级，结论：**两套图内容不同**，不是同一批地图文件换了编号。
3. **肉眼比对**：`docs/sheets/_unity_scenes.png` 与 `docs/sheets/_my_scenes.png` 两套总表并排看，
   画风一致、都是这个游戏的地图，但具体场景对不上。

所以**不能**按编号或最近邻去替换我现有的场景图 —— 那会把地图和场景名张冠李戴。
如果以后要用这 79 张，正确做法是当作**新增**地图（重新规划岛屿归属），而不是替换。

## 五、结论与建议

* 这一轮**没有**从这份包里搬任何东西进游戏：能搬的（火多比战斗表）不属于我现在的 11 只形态；
  背包界面是第三方 UI；地图是另一套、对不上号。
* 已把它整理成可复用的素材库（`_unity_tex/` + 解析工具），以后需要**新增**地图时可以直接用。
* 如果后续要继续挖：下一步是解析 `level*` 场景文件里的 GameObject/RectTransform 层级，
  那样能拿到它**自己的**背包界面结构（但那也不是"原版"的）。

**教训（和前面几次是同一类）**：
我第一次跑内容匹配得到"0 对配对"，差点据此下结论"两套图不同"。
复核时发现匹配脚本自己写错了（manifest 里是 `scene_01.png`，我却用 `scene_1\.` 去匹配），
修好之后**结论没变**，但那是运气 —— 如果当时结论正好相反，我就会基于一个坏工具做决定。
**工具给出"空结果/否定结果"时，必须先证明它有给出肯定结果的能力**（这次靠"自己和自己比必须是 0"这条自检兜住了）。
